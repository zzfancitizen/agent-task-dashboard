# Agent Relay · Agent Task Board

[中文](README.md) | **English**

Publish a complete delegation when you need more agent capacity. A colleague with spare quota claims it, runs their own Codex CLI or Claude Code, and returns the results to the publisher.

**Use GitHub Pages for everyday browsing. Your existing agent helps publish; claimers download a package from the page, extract it, and run it. No separate backend, database, or local website is required.** Hosted components are GitHub Issues, Actions, Pages, and Release attachments. Company GitHub hostnames are supported.

The board uses your company's GitHub SSO and native access controls. There is no separate participant roster, and ordinary participants do not need repository write access. They need to read the board repository, create Issues and comments, and read the source and resources referenced by a task. Actions writes Release artifacts.

## 1. Start here

| What you want to do | Where to start |
| --- | --- |
| Browse tasks | Open the GitHub Pages URL supplied by your administrator; a browser is enough |
| Publish work | Open the publish entry, set up the publishing integration once, then let your existing Codex / Claude session prepare and publish |
| Pick up a task | Open its details, select the claim button and Windows / macOS / Linux, then download, extract, and run the package |
| Review a delivery | Follow the GitHub notification or open a task awaiting review; ask your original agent to sync and inspect the result |
| Deploy a board | Follow the [administrator setup](#deployment) to import the repository and enable Actions and Pages |

The complete workflow is: **agent prepares a proposal → publisher confirms → publish → claim → local execution → submit artifacts → publisher accepts**.

The parchment cards use one to three stars for S / M / L task size and stamps for actual task status. The page is an asynchronous snapshot generated by Actions. Downloading a package does not reserve a task; the local tool checks the live task and claim before execution.

The hostname `git.company.example`, repositories `team/agent-task-board` and `team/demo-api`, Issue `42`, paths, and UUIDs in this guide are examples. Replace them with your actual values. Demo mode contains fictional tasks and does not allow real claims.

The current website and wizard menus use Chinese labels; this guide explains their meaning. Installation menus use `1` for official instructions, `2` to retry, `0` to cancel, and offer `3` for a consented package-manager installation when available.

## 2. Publish through your existing agent

### 2.1 First-time setup

1. Open the deployed GitHub Pages board and select **发布任务** (publish task).
2. Select **下载发布接入包** (download publisher setup), choose your operating system, and download the ZIP.
3. **Extract the entire ZIP** into a folder. Do not run a file from inside the archive viewer.
4. Open the appropriate starter file and follow the prompts for required tools, GitHub login, and company SSO authorization.
5. Choose Codex or Claude Code, then select the **source project directory** where the publishing integration should be installed.
6. Follow your provider's project-hook trust requirements and reopen or resume the original project session to activate the integration.

You can also use **复制指引给我的 Agent** (copy instructions for my agent) on the page and let an existing CLI agent perform the setup. The integration adds a project skill, a short rule, and session hooks while preserving unrelated rules and settings. Set it up once for each source project that needs it.

See [first-run guidance](#first-run) for installation behavior. The wizard does not register provider accounts or supply quota. Installing the publishing integration does not publish a task.

### 2.2 Everyday publishing: describe the work

Work normally in the configured Codex / Claude session, or ask something like:

> Prepare this testing work as a delegation. Include the full prompt, code version, resources, allowed changes, and acceptance criteria. Show me the proposal first so I can decide whether to publish it to the task board.

The skill guides the agent to assess whether the work can be handed off independently. When appropriate, it prepares a local proposal containing:

| Content | Purpose |
| --- | --- |
| Goal, background, and complete prompt | A claimer can start without seeing your previous conversation |
| Source repository and pinned commit | Both machines use the same execution baseline |
| Resources and content hashes | Provide the required material and verify the downloaded bytes |
| Allowed write paths | Define the directories and files this task may change |
| Acceptance criteria, commands, and outputs | Explain how to evaluate completion and what must be returned |
| Local binding to the original session | Find the exact original Codex / Claude session when the result arrives |

The agent should show the concrete proposal and reason for delegation, then ask whether to publish. **It publishes only after your explicit agreement to that proposal.** Task complexity, a hook event, or installing the skill does not count as consent. You can choose to continue locally.

The agent collects the repository, commit, resource hashes, and exact session association to reduce manual copying. It still needs to write the goal, context, and acceptance criteria from the current work; the program cannot infer your intent by itself. Relevant uncommitted changes must be handled first, not silently omitted. The delegated commits and resources must also be available from the remote.

A successful publication returns a GitHub Issue link. Actions validates it and refreshes Pages. If it has not appeared yet, check the Issue and workflow progress. After an uncertain network response, retry the **same proposal** and retain local state to avoid duplicate tasks.

### 2.3 How session context is handed over

The Issue contains an independent task package. The original session ID, credentials, and full conversation remain on the publisher's computer; they are not included in Pages or the execution download. The hook records the exact session and directory reported by the provider. It does not guess the latest session.

The claimer runs a new, independent agent session. The original session reads the returned artifacts and continues the publisher's work. A task published through Codex can therefore run through compatible Claude Code, but this does not migrate an entire Codex session into Claude.

### 2.4 Change or cancel a task

The task package is frozen once Actions confirms it. Editing the Issue body does not change its confirmed prompt, commit, or resources. Ask the publishing agent to cancel the old task and publish a new task ID when the work changes. The advanced cancellation command is:

```sh
./bin/taskboard cancel 42
```

Cancellation invalidates later submissions, but cannot remotely terminate an agent already running on another computer. Accepted tasks remain as history.

## 3. Claim and run from the website

### 3.1 Download and open the execution package

1. Open an available task on Pages and read its goal, resources, allowed changes, and acceptance criteria.
2. Select **领取任务** (claim task), choose **Windows / macOS / Linux**, and download the task ZIP.
3. Extract the entire ZIP and keep its files together.
4. Open the starter for your operating system:

| Operating system | Starter | How to open it |
| --- | --- | --- |
| Windows | `Start-Taskboard.cmd` | Double-click to open a command window |
| macOS | `Start-Taskboard.command` | Double-click to run in Terminal |
| Linux | `Start-Taskboard.sh` | Choose the file manager's run-as-program option; wording varies by desktop |

The package contains starter scripts, a Python runtime source archive, and task locator metadata. It contains no GitHub token or provider login. It is an inspectable script ZIP, not a signed installer or standalone `.exe`. macOS / Windows may show download-origin or execution prompts; Linux may require enabling execution in file properties. Follow company device policy. The tool does not disable these protections.

<a id="first-run"></a>
### 3.2 First run: guided installation and login

The starter checks for **Python 3.11+** first. If Python is missing, it offers the official installer page and retry/cancel choices. After installation, return to the wizard and retry, or reopen the starter if necessary.

The wizard then checks Git, GitHub CLI (`gh`), and your selected Codex / Claude Code. When a tool is missing, it offers installation guidance. Where a supported package manager is available, it shows the installation and asks for consent; otherwise, it opens the official instructions. Installation is not silent. Use your normal administrator process for managed company devices.

The wizard guides GitHub browser login and company SSO authorization, plus the selected agent's native login flow. Check the GitHub account, provider account, and quota you intend to use. Existing valid logins are reused. After the first setup, later tasks usually only need an agent choice and execution.

The wizard configures the board from the package and shows the source and resource repositories required for this task. SSO login does not automatically grant access to every source repository; use your company's access process if a repository is unavailable.

### 3.3 Choose an agent and wait for delivery

After you choose a supported **Codex** or **Claude Code**, review the repositories and verification instructions and confirm execution. The tool:

1. Reads the confirmed task from GitHub and checks its revision and digest; an outdated package is rejected.
2. Requests a claim and waits for Actions to confirm that your account owns the attempt.
3. Prepares pinned source code and resources in an independent directory and verifies hashes.
4. Requests execution start, then runs your local agent after confirmation, using your provider account's quota.
5. Runs verification commands and checks the write scope and required artifacts.
6. Submits compressed artifacts through Issue comments. Actions validates them, saves Release attachments, confirms submission, and refreshes Pages.
7. Shows the submission result and GitHub entry. The publisher receives a new result-comment notification and can review the delivery.

Downloading is not a confirmed claim. If someone else is confirmed first, the tool reports the current state and does not start duplicate execution. When Actions is queued, the wizard waits or offers retry. It reports submission only after confirmation.

The local tool does not change your existing source checkout or automatically merge or deploy. Source-project dependencies still need to follow the task's instructions; the general setup wizard cannot infer every project's environment.

### 3.4 Large artifacts, interruptions, and retries

The current transfer is suited to code, patches, documents, and test reports. **The compressed artifact ZIP must be at most 1 MiB**. Each uncompressed file is limited to 20 MiB, and total uncompressed content to 100 MiB. Excess size is rejected before posting chunks, and the local files are retained. Avoid tasks that require large binary deliverables; do not remove required verification evidence merely to fit the limit.

If the network or Actions is temporarily unavailable, retain the extracted package and local state. Retry through the wizard or reopen the same package. Prepared artifacts are reused; waiting for confirmation does not by itself rerun the agent. If execution is reported as uncertain, inspect the local processes and records first. The tool will not blindly start a second execution.

To stop, press Ctrl+C in the running terminal. The tool makes a best effort to request release. If the network is unavailable, check the Issue state, then release through your agent or the [advanced commands](#cli-execute). See [state rules](#reference) for claim expiry and attempt limits.

## 4. Review results, return to your session, and accept

### 4.1 GitHub notifications and delivery on Pages

After confirming artifacts, Actions posts a separate result comment mentioning the publisher and executor, with a result ID, download links, and a note that acceptance is pending. Your GitHub notification settings determine whether this produces email or push notifications.

Open a task awaiting review on Pages to inspect its summary, assumptions, unresolved items, verification records, and artifact links. Default outputs are `changes.patch`, `summary.md`, and `verification.json`, plus any additional files required by the task.

**Successful submission means delivered; acceptance means completed.** Apply patches, merge PRs, and deploy through your project's existing processes.

### 4.2 Retrieve results in the original session

After the notification, return to the Codex / Claude session that published the task and say, for example:

> Sync the task board's delivery, inspect this task's changes and verification evidence, then continue the current work. Explain your acceptance assessment first.

The publishing integration supplies the exact local task/session association. The agent can run `sync`, download and verify your results, then read them in the current session. Hooks only announce new results already synced locally and bound to that session. They do not poll the remote or make extra model calls.

To download manually, first prepare the CLI as described in [advanced configuration](#setup) and use the same `--home` as the publishing integration. Download-wizard users can simply ask their original agent to use the complete tool entry supplied by the hook, without finding an installation directory themselves:

```sh
./bin/taskboard sync
```

This retrieves only confirmed `submitted` / `accepted` results for tasks published by the current GitHub account. It prints the local inbox path and does not invoke a model.

If the original session has exited or is known to be idle, you can explicitly resume the exact original session:

```sh
./bin/taskboard sync --resume
```

`--resume` uses the publisher's provider quota and allows up to 600 seconds per continuation. Do not run it while another terminal is using the same session. The tool does not use `--last`, wake offline computers, or run a persistent listener. Without a binding or an available original session, results can still be downloaded and handed to an agent manually.

If delivery is interrupted and its outcome is uncertain, the tool preserves `unknown` status. Inspect the original session first; it does not automatically redeliver or clear state to force a replay.

### 4.3 Accept or request rework

Ask the publishing agent to compare the delivery with the original task, current code, and verification evidence, then submit acceptance or rejection according to your decision. Only the publisher can accept, reject, or cancel. Only the current executor can submit or release. These are task ownership rules, not a separate participant permission system.

Advanced commands use the **result UUID** from the GitHub result comment or local inbox:

```sh
./bin/taskboard accept 42 --result RESULT_UUID
./bin/taskboard reject 42 --result RESULT_UUID --reason "Please add the missing zero-amount boundary test and verify again"
```

The result UUID is not the Issue number, task ID, attempt ID, or session ID. Review requests also await Actions confirmation. Rejection retains the old artifacts and reopens the task if attempts remain. `accept` does not apply patches, merge, or deploy code.

<a id="rankings"></a>
## 5. Guild leaderboards

The board shows two top-ten lists for its current confirmed task snapshot:

| Leaderboard | Counting rule |
| --- | --- |
| Most published | Distinct task IDs, excluding cancelled tasks |
| Most completed | Distinct accepted task IDs, credited to the executor of the accepted attempt |

Repeated submissions, retries, and comments do not increase counts. Results awaiting acceptance are not completed tasks. Usernames are compared without case sensitivity; ties use stable ordering. Rankings update with the Actions snapshot and do not represent token usage, task difficulty, or invented rewards.

## 6. Administrator: deploy once

### 6.1 Prepare the repository and runner

1. Import the complete project into your company repository's **default branch**, including `.github/`, `launchers/`, and `integrations/`.
2. Enable Issues, Actions, and Pages. Use native company GitHub policy to let participants read the repository and create Issues and comments.
3. Allow the workflow's `contents: write`, `issues: write`, and `pages: write` permissions. These belong to Actions; ordinary participants do not need those repository roles.
4. Provide a runner. GitHub.com defaults to `ubuntu-latest`; GitHub Enterprise Server defaults to your existing `self-hosted` runner.

The runner needs Python 3.11+ and GitHub CLI. The `Check task board` workflow also needs Node.js 18+. No Python or frontend third-party packages are required. If external Actions are unavailable internally, replace `actions/checkout@v4` in the workflows with your company's mirrored action.

Configure these repository variables in **Settings → Secrets and variables → Actions → Variables**:

| Variable | Value |
| --- | --- |
| `TASKBOARD_RUNNER` | Optional company runner label, such as `corp-linux`, without extra quotes |
| `TASKBOARD_PAGES_ENABLED` | Set to the string `true` after the first branch generation to request Pages builds |

Do not configure a participant roster or assign write / maintain / admin roles just to use the board. Do not upload members' GitHub tokens, provider login files, or model API keys. Actions uses its GitHub-provided credentials to store artifacts and publish the page.

### 6.2 Enable Pages

1. Open **Actions → Task board controller → Run workflow** and run it once.
2. A successful run creates `taskboard-state` for confirmed state and `gh-pages` for the page, `tasks.json`, and download tools.
3. In **Settings → Pages → Build and deployment**, choose **Deploy from a branch**, with **`gh-pages` / `/ (root)`** as the source. This design uses a public site and does not add an application login screen.
4. Set `TASKBOARD_PAGES_ENABLED` to `true`, then run the controller again.
5. Share the actual Pages URL shown by GitHub. Enterprise domains and paths depend on your company setup.

Task and command comments trigger updates. Artifact chunk comments remain in the Issue until the final submission command triggers processing. Manual runs and recovery scans at minutes 17 and 47 of each hour are also available; scheduling is not real-time.

If company policy disables the Pages build API, use the generated `gh-pages` branch with the existing company Pages publishing process. The controller is the only writer of confirmed state. Do not edit `taskboard-state/state.json` manually. See the [GitHub-only architecture notes](docs/github-only.md) for details.

## 7. Advanced configuration and CLI

The website's download wizard performs the usual setup. This section is for existing developer environments, scripting, and recovery; ordinary claimers do not need to type these commands. The `./bin/taskboard` examples run from the Taskboard source checkout's root, not the downloaded ZIP or task source directory. The installed skill's `context` returns the complete `taskboard_argv`, including the runtime path and correct `--home`; agents should use that entry directly.

### 7.1 Manual installation and board configuration

Obtain the source and run commands from this project's root. The macOS / Linux examples use `./bin/taskboard`; on Windows, replace it with `python -m taskboard` from the same directory. No `pip install` or `npm install` is required.

```sh
gh auth login --hostname git.company.example --git-protocol https --web
gh repo clone https://git.company.example/team/agent-task-board
cd agent-task-board
./bin/taskboard init \
  --repo team/agent-task-board \
  --hostname git.company.example \
  --allow-repo team/demo-api \
  --agent codex
```

`--repo` identifies the board repository as `owner/repo`. `--hostname` is a GitHub hostname without a scheme, port, or path; it defaults to `github.com`. Repeat `--allow-repo` for source/resource repositories the local tool may read or execute. The board repository is included automatically. Run `init` again with the same board to add allowed repositories. Native access is still enforced by GitHub.

The manual CLI defaults to `~/.local/share/taskboard`; override it with `TASKBOARD_HOME` or the shared `--home PATH` option. The download wizard uses the operating system's local user-data directory and separates each board's configuration; see the [deployment notes](docs/github-only.md#下载包与首次引导) for paths. One state directory belongs to one board. For manual multi-board use, choose separate directories and use the same directory for integration installation and subsequent commands. `--agent` sets a default provider, while `run` still requires an explicit choice.

### 7.2 Install the publishing skill, rule, and hooks

```sh
./bin/taskboard install-integration --provider codex --project /absolute/path/to/demo-api
./bin/taskboard install-integration --provider claude --project /absolute/path/to/demo-api
```

Run only the command for each provider you need. Codex uses project `.agents/skills/taskboard-publish/`, `AGENTS.md`, and `.codex/hooks.json`. Claude uses `.claude/skills/taskboard-publish/`, `CLAUDE.md`, and `.claude/settings.json`. The installer preserves unrelated settings and adds marked rule blocks plus `SessionStart` / `UserPromptSubmit` hooks. Reload and trust hooks according to the provider's requirements.

Hooks receive the real session and cwd on stdin, store the local association, and give the agent the proposal-tool entry. They do not upload transcripts, search for an arbitrary latest session, publish tasks, or invoke a model on a timer. The first user message after hooks become active can also supply the exact association. If the provider has not reloaded the hooks, resume the same original session.

### 7.3 Agent proposals and explicit publication

These are low-level interfaces for agents and script authors. Everyday users do not need to fill in JSON. Write a UTF-8 goal file outside the source directory:

```json
{
  "goal": "Add boundary tests for discount calculations",
  "context": "Existing amount and discount types are defined in the code. Preserve the public interface.",
  "acceptance": ["Cover zero amount, zero discount, and invalid input", "Existing tests still pass"],
  "delegation_reason": "The test work is independent, with pinned code and clear acceptance criteria"
}
```

```sh
./bin/taskboard propose \
  --workspace /absolute/path/to/demo-api \
  --goal-file /absolute/path/to/proposal-goal.json \
  --title "Add discount boundary tests" \
  --provider codex --session ORIGINAL_SESSION_UUID \
  --resource docs/discount-rules.md \
  --write-path tests \
  --command-json '["python3", "-m", "unittest"]' \
  --size M --category code
```

Resource, write-path, and command options are repeatable. Verification commands are argv arrays, not shell strings. Use the exact session supplied by the provider/hook. Goal JSON can also include `required_outputs`. After a fresh integration installation, the skill helper's `context --callback UUID` returns exact `excluded_paths` that may be copied into the goal JSON to exclude unchanged installer-managed files. These exclusions cannot hide source changes. The everyday skill handles this; direct `propose` callers must ensure the source check can pass.

The proposal is local only. After showing it and receiving the user's explicit agreement, run:

```sh
./bin/taskboard publish-proposal PROPOSAL_UUID --approved
```

Publication is refused without `--approved` or if proposal changes invalidate its digest. Retrying the same proposal reuses its task identity. The installed skill's helper can obtain the exact session through a local hook callback, avoiding manual UUID lookup.

### 7.4 Manual task packages and managed source sessions

Advanced use still supports exporting JSON from the manual Pages form or preparing a pinned task using [task-v1.json](docs/examples/task-v1.json):

```sh
./bin/taskboard validate task.json
./bin/taskboard publish task.json
./bin/taskboard publish task.json --session ORIGINAL_SESSION_UUID --agent codex --workspace /absolute/path/to/demo-api
```

Exporting a form does not create an Issue. `publish` is an explicit publication command. Supply all three original-session binding options together, or omit all three when no session is available. If binding was omitted, rerun the exact same task package in the same local configuration with the binding options.

A task contains an independent prompt, an HTTPS source repository on the same GitHub host, a full 40-character commit SHA, resource paths and SHA-256 hashes of their content at that commit, a write scope, execution requirements, and acceptance checks. Only committed inputs are supported; `source.workspace_patch` must be `null`. Resource destinations cannot overwrite existing checkout files.

Task/request JSON is limited to 48 KiB. Runtime limits are 1–14400 seconds and 1–5 attempts. The tool generates `changes.patch`, `summary.md`, and `verification.json`; the agent need not create them in the source checkout. Additional required outputs must be inside the workspace and permitted by `write_paths`.

The managed source-session entry is also retained and captures the session from real provider events:

```sh
./bin/taskboard start --agent codex --prompt work.md --workspace /absolute/path/to/demo-api
```

This is an advanced noninteractive flow with a default 14400-second timeout, adjustable with `--timeout`. The existing interactive session's skill integration is the everyday publishing path. `start` neither guarantees publication nor removes the confirmation requirement.

<a id="cli-execute"></a>
### 7.5 Claim, execution, and recovery commands

```sh
./bin/taskboard run 42 --agent codex
./bin/taskboard run 42 --agent claude --wait 600
./bin/taskboard claim 42 --wait 180
./bin/taskboard release 42 --reason "I cannot continue this task right now"
```

`run` claims, executes, verifies, and submits automatically. Each confirmation stage waits 180 seconds by default; `--wait` accepts 0–600 seconds. `claim` defaults to 0 seconds, queues a request, and does not start an agent. The claim is successful only after `Claim confirmed.` or confirmed state names you as the owner.

On `REQUEST_PENDING`, wait for Actions and rerun the same command. The tool keeps the original request, workspace, and prepared artifacts, preventing duplicate execution merely because confirmation is delayed. Do not delete local state to retry.

The legacy HTTPS manifest entry remains available for already-uploaded, valid Release artifacts:

```sh
./bin/taskboard submit 42 /absolute/path/to/result.json
```

This does not execute an agent or upload local files. The manifest must match the current task, revision, digest, attempt, and base commit, and contain board Release artifact HTTPS URLs and hashes. Normal execution uses the comment transfer bridge and needs no participant Release write permission.

The old macOS URL-handler commands, `install-launcher` / `open-url`, remain as compatibility entries. The website ZIP flow does not depend on registering a URL scheme or running a local service.

## 8. States, limits, and command reference

| State | Meaning | Next step |
| --- | --- | --- |
| `open` | Available to claim | Download and run the task package |
| `claimed` | Claim confirmed | Current claimer prepares and starts execution |
| `running` | Execution start confirmed | Wait for local execution and submission |
| `submitted` | Delivered, awaiting acceptance | Publisher syncs, reviews, accepts, or rejects |
| `accepted` | Accepted; counted as completed | Integrate through normal project processes |
| `cancelled` | Cancelled by the publisher | Publish a new task for new work |
| `failed` | Terminal, such as exhausted attempts | Review the history and decide whether to publish a new task |

A claim's lease starts when Actions confirms it and lasts the task's runtime limit plus 600 seconds of preparation time. A confirmed claim consumes an attempt; release or expiry does not refund it. Expiry is processed on a later controller scan. An old attempt cannot replace a newer result. The page groups `claimed` and `running` as in progress.

| Command | Purpose |
| --- | --- |
| `init --repo OWNER/REPO --hostname HOST` | Manually configure a local board |
| `install-integration --provider AGENT --project PATH` | Install publishing into an existing agent project |
| `propose ...` | Prepare a complete local proposal |
| `publish-proposal ID --approved` | Publish the proposal after user agreement |
| `validate FILE` / `publish FILE` | Validate or explicitly publish a manual task package |
| `start --agent AGENT --prompt FILE --workspace PATH` | Advanced managed source session |
| `claim ISSUE [--wait SECONDS]` | Request a claim without running |
| `run ISSUE --agent AGENT [--wait SECONDS]` | Claim, execute, verify, and submit automatically |
| `submit ISSUE FILE` | Submit an already-uploaded HTTPS result manifest |
| `sync [--resume]` | Download your results; optionally resume the exact original session |
| `accept ISSUE --result UUID` | Publisher accepts |
| `reject ISSUE --result UUID --reason TEXT` | Publisher rejects |
| `release ISSUE --reason TEXT` | Current claimer releases |
| `cancel ISSUE` | Publisher cancels |

Prefix commands with `./bin/taskboard`. Shared options are `--repo`, `--hostname`, and `--home`; they usually need not be repeated after setup. Use `COMMAND --help` for exact arguments. There is currently no `--watch`, browser token-storage write flow, or automatic merge.

<a id="troubleshooting"></a>
## 9. Troubleshooting and recovery

| Symptom | What to do |
| --- | --- |
| Double-clicking the ZIP only shows its contents | Extract everything, then open the appropriate `Start-Taskboard` file with the other files in the same folder |
| The OS blocks a downloaded script | Follow company policy for download-origin/execution prompts. On Linux, check executable permission in file properties; do not disable system protections |
| An installed tool is still missing | Retry in the wizard, or reopen the starter if PATH has not refreshed. Managed devices may require administrator installation |
| GitHub login fails or `GITHUB_403` | Check the host, account, SSO, Issue/comment permissions, and source read access. Actions failures also require checking the workflow's own write permissions |
| Pages lacks a new task or result | Check the controller, `gh-pages/tasks.json`, and Pages build. An administrator can run the controller manually. Demo data is not live data |
| Actions stays queued | Check `TASKBOARD_RUNNER`, runner availability, and organization policies; wait rather than creating duplicate tasks |
| The package is outdated or the task is already claimed | Refresh the deployed board and check live status. A new download does not take over another person's valid claim |
| `TASK_PENDING` / `REQUEST_PENDING` | Retain local files, wait for Actions, and retry the same package or command |
| Artifacts exceed the 1 MiB compressed limit | Inspect retained local files and remove only unnecessary large outputs. If required deliverables exceed the limit, the publisher must revise the task |
| `CONFIG_CONFLICT` / `LAUNCH_REPOSITORY_MISMATCH` | Check board host and repository. Use separate `--home` directories for manual multi-board use |
| `REPOSITORY_NOT_ALLOWED` | The wizard configures repositories from the confirmed task. With the manual CLI, add `init --allow-repo OWNER/REPO` and verify native GitHub read access |
| `INCOMPATIBLE_AGENT` | Choose a supported Codex / Claude provider. An incompatible choice does not consume a claim attempt |
| `NOT_OWNER` / `ATTEMPT_EXPIRED` / `STALE_ATTEMPT` | Check ownership, expiry, and remaining attempts. An old execution cannot submit under a newer attempt |
| `RESOURCE_HASH_MISMATCH` / `RESOURCE_COLLISION` / `UNSAFE_PATH` | Check pinned commits and resource content. Resources cannot overwrite checkout files or point into `.git`; workspace symlinks are currently unsupported |
| `VERIFICATION_FAILED` / `WRITE_SCOPE_VIOLATION` / `OUTPUT_MISSING` | Inspect the reported `checks/` directory and `artifacts/verification.json`. Failure is not submitted as a successful result |
| Network fails during upload or submission | Keep the files and retry the same package/command. Recovery reuses matching artifacts and requests, not different bytes under the same name |
| `EXECUTION_UNKNOWN` / `LOCAL_BUSY` | Inspect existing processes and local records before starting anything else. Stop and release if appropriate, then wait for a new valid claim |
| `PUBLISH_UNKNOWN` / `TASK_CONFLICT` | Check whether the Issue already exists. Retry the same proposal/task content; changed content needs a new task ID |
| The original agent does not show the publishing skill | Check the project and provider installation, trust/reload hooks as required, and resume the original session |
| The original session does not receive results automatically | A GitHub notification does not start a local agent. Ask the original session to sync; hooks announce only results already present locally |
| `sync` finds nothing or no session is bound | Verify you are the publisher, delivery is confirmed, and the board is correct. Unbound results can still be downloaded and used manually |
| Continuation is `unknown` | Check whether the original session received the result. Do not clear state to force another delivery |

## 10. Development checks and current scope

These steps are for development and validation. Everyday users open the deployed GitHub Pages site.

```sh
python3 -m unittest discover -s tests -v
node --test tests/test_*.mjs
python3 -m compileall -q taskboard scripts
```

Optional local visual preview:

```sh
python3 -m http.server 8080 --bind 127.0.0.1 --directory site
```

Open the [local development preview](http://127.0.0.1:8080/) and explicitly enter demo mode. Download assets are generated by the controller's site build; serving the source `site/` directory alone is not the complete deployment output.

- Only independent `subtask` delegation is supported, not complete session migration, uncommitted workspace patches, or arbitrary recursive delegation.
- The local tool checks hashes, paths, write scope, and execution identity. `write_paths` is a pre-submission check, not an OS ACL. Task code and verification commands run with local user permissions and must come from work you have authorized.
- Members retain their own GitHub and provider logins. Pages, task packages, and download scripts contain neither these credentials nor original-session logs.
- Python/Node tests use temporary Git repositories and simulated GitHub/provider boundaries without spending model quota. Native Windows / Linux desktop installation and double-click flows, company SSO, actual runner/Pages operation, and two-account billing still need target-environment validation. This project does not claim those live checks have already been performed.

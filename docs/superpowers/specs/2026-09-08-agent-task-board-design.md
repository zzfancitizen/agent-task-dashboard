# Agent Task Board 设计

日期：2026-09-08

状态：产品方向已获用户同意；本文将其细化为工程设计。尚未实现、部署或进行真实账号联调。

## 1. 目的与已确认的需求

公司对个人 agent 额度进行限制，同一组内会同时出现额度不足和额度剩余。产品让任务在成员间流转，利用剩余额度完成可交接的工作。

已经确认：

- 团队日常使用 GitHub，任务描述与资源链接可以放在组织私有仓库。
- 一个任务对应一个 Issue；定制界面改善发布、认领和交付体验。
- 发布者可以是 agent。它根据额度压力、独立性、交接成本、验收成本和等待时间选择本地执行或委派。
- 发布任务需要完整 prompt、resources、环境要求、验收标准和停止条件。
- 认领者使用自己本机的命令行 agent，例如 Codex CLI 或 Claude Code。
- 结果需要关联并返回发起者原会话，供原 agent 验收和继续。
- 任务复杂度不是自动发布的唯一条件；执行完成与验收完成是不同状态。
- 子任务委派必须预留整合额度；整项移交需要另行明确谁负责最终交付。

成功标准是可验收成果的交接，而非最大化消耗 token。试点同时记录发布者的额度消耗、人工介入时间、认领等待时间、验收成功率，以及可获得的执行用量。不同产品的用量和计费单位分别记录，不把它们强行换算成相同的余额。

## 2. 首版边界与交付顺序

首版产品包含私有任务大厅、GitHub Issue 记录、本地 CLI 启动器和小型协调服务。

先实现一个可独立验证的核心切片：任务包发布、唯一有效认领、独立目录执行、结构化交付、原会话结果投递及验收。核心联调使用本地协调服务、可替换的 GitHub 接口和确定性的模拟 agent。真实 CLI 的接入通过明确的适配器进行。

之后将同一接口接入任务大厅、原生启动入口和真实组织账号。界面不另建一套任务状态逻辑。

首个切片的工程选择：

- Python 3.11+；核心逻辑、本地状态、协调服务和测试仅使用标准库。
- SQLite 保存协调状态、认领记录和持久化事件。
- 通过现有 GitHub CLI 调用 GitHub API；不新增第三方依赖。
- 初始开发与联调环境为 macOS/Linux；Windows 的进程管理与启动入口作为后续平台适配验证。
- CLI 适配器先实现 Codex，再按同一契约实现 Claude Code。
- 本地协调服务仅绑定 loopback。多人服务上线必须先完成身份认证、访问控制、HTTPS 与部署验证，不能将本地联调服务直接暴露到公网。

不包含：自动认领他人的额度、凭据共享、跨用户复制完整会话、自动合并代码或部署、任意层级递归委派、自动购买额度、精确预测所有产品剩余额度。

## 3. 系统职责

| 部件 | 职责 |
| --- | --- |
| 任务大厅 | 浏览、筛选、认领、启动、查看产物和验收状态 |
| GitHub Issue | 人可读的任务包、讨论、产物链接与状态投影 |
| 协调服务 | 任务版本、唯一有效认领、重试次数、状态转换、结果事件和幂等记录 |
| 本地启动器 | 会话绑定、资源准备、执行 CLI、心跳、停止、结果整理及接收 |
| CLI 适配器 | 解析真实 session ID、启动/恢复会话、识别完成与失败、传递运行约束 |

认领及状态转换以协调服务为准。GitHub Issue 展示其投影；不能通过“先读 assignee、再写 assignee”实现互斥。GitHub 暂时不可用时，已经持久化的转换仍可恢复同步。

Issue 的人工评论不自动变成 agent 指令；手工修改关键字段也不直接修改已发布任务版本。修改任务通过新版本发布，保留原版本和在途执行的对应关系。

创建新版本必须沿用 task ID，revision 递增 1。旧版本处于 claimed、running 或 submitted 时，先完成取消或验收处置；不能让新旧版本同时成为可执行的当前版本。协调服务在同一事务内检查当前版本并切换指针。

## 4. 自主委派规则

Agent 负责提出并解释委派选择；启动器落实用户预先设置的权限和数量限制。

适合委派的任务需要满足：输入可以独立提供、资源可访问、运行环境可准备、结果能验收、允许等待认领。Agent 在任务包中写明委派原因及验收方式。

自动发布的策略包含允许的任务仓库、资源仓库、任务类型、同时在途任务数和最多尝试次数。缺少策略时可以生成本地草稿，但不能推断用户已允许向任意仓库自动发布。

剩余额度来自工具提供的实际数据或用户声明的预算，并保留来源和采集时间；不可获取时标为未知。委派前保留打包、接收结果和验收的预算，已耗尽时允许进入待人工验收状态。

首个切片只执行 `subtask` 模式。`handoff` 的最终责任人、验收和会话接续流程尚不属于这个切片，输入该模式时返回 `UNSUPPORTED_MODE`，不能静默按子任务处理。

## 5. 任务包协议 v1

任务示例见 `docs/examples/task-v1.json`。

| 字段 | 约束 |
| --- | --- |
| `schema_version` | 固定为 1 |
| `task_id` | 发起端生成的 UUID；创建重试沿用同一个值 |
| `revision` | 从 1 开始的正整数；发布后内容不可变 |
| `mode` | 首个切片仅支持 `subtask` |
| `title`、`prompt` | 非空；prompt 包含目标、边界、资料用法和验收要求 |
| `delegation_reason` | 人可读的委派理由，不用于绕过策略 |
| `source` | 仓库、完整基准 commit、允许修改路径；必要时引用未提交改动包 |
| `resources` | 资源类型、不可变定位、相对落盘路径和内容 SHA-256 |
| `execution` | 支持的 agent、时长上限和最多尝试次数 |
| `acceptance` | 验收命令的 argv 数组、必要产物及人工检查说明 |

资源首批仅支持固定 commit 的仓库文件和内容校验通过的任务附件。网页材料先固定为文件快照，避免执行期间远端内容变化。凭据通过执行者本机已有配置提供，任务包只描述所需访问能力。

所有目标路径必须位于任务目录内：拒绝绝对路径、`..`、符号链接逃逸和重名覆盖。命令按 argv 执行，不将 prompt、标题、链接或任务提供的字符串拼成 shell 命令。

允许修改路径是验收约束。独立工作目录本身并不是操作系统沙箱；运行权限由 CLI 的现有机制实施。适配器不能满足任务所需约束时返回 `UNSUPPORTED_EXECUTION_PROFILE`，不能用取消全部限制的参数补救。

规范化摘要采用 UTF-8、排序键、无额外空白的 JSON 序列化后计算 SHA-256。对象键顺序不影响摘要，数组顺序保留。任务版本、prompt、资源定位、验收条件与摘要一起冻结。

## 6. 会话关联

发起端在本地保存：

`task_id + revision → provider + origin_host_id + session_id + workspace + delegation_checkpoint`

`delegation_checkpoint` 包括任务摘要、代码基准和发布时的本地工作区状态摘要。Session ID 必须来自启动器捕获的 CLI 事件或用户明确绑定的已存在会话，不能由模型猜测。

管理中的发起会话由 `taskboard start` 创建。启动前生成 origin run ID，经 `TASKBOARD_ORIGIN_RUN_ID` 传给 agent 可调用的本地发布命令；启动器捕获真实 session 事件后建立 run ID 到 session 的映射。Agent 发布时提交任务包，原会话关联由本地程序自动补齐。映射尚未建立时返回 `ORIGIN_NOT_READY`，不让模型填写一个推测的 ID。

认领方使用自己的 session ID。它只提交任务 ID、版本和执行尝试 ID；原 session ID 和本地绝对路径无需放进供认领者读取的 Issue。

首个切片只自动接续启动器管理的发起会话。外部会话可以绑定以展示关联，但在无法证明独占访问时只保存待接收结果，不自动恢复。

所有由启动器管理的源会话执行与结果投递共用 `provider + host_id + session_id` 对应的跨进程文件锁，锁覆盖状态核对、启动/resume、运行和确认持久化。锁按会话而非任务划分。无法确定是否有未受管理的进程正在使用同一会话时，结果继续排队。

## 7. 生命周期与认领

业务状态：

`draft → open → claimed → running → submitted → accepted`

补充状态为 `cancelled` 和 `failed`。`submitted` 表示成果已提交，`accepted` 才表示已验收。

- `draft → open`：任务校验及发布策略通过，任务包与发布事件在同一事务持久化。
- `open → claimed`：单个 SQLite 事务分配 `attempt_id`、随机 lease token 和到期时间。
- `claimed → running`：启动器确认资源和权限检查通过，CLI 已启动。
- `claimed/running → open`：释放或心跳过期且仍有重试额度；旧认领失效。
- `claimed/running → failed`：不可恢复失败或达到最多尝试次数。
- `running → submitted`：提交者、版本、attempt、lease 和状态全部匹配；全部必要产物已独立存储且完整性校验通过。
- `submitted → accepted`：发起端在当前代码状态下完成验收，并明确指定当前成果。
- `submitted → open/failed`：发起端拒收并给出具体原因；按重试额度决定下一步。

同时只能有一个有效认领。失联进程可能尚未物理停止，因此严格保证的是“只有当前 lease 能更新状态或提交结果”。启动器连续心跳失败应终止本地执行；旧 attempt 的迟到结果返回 `STALE_ATTEMPT`，不得覆盖新执行。

心跳默认每 30 秒一次，lease 默认 120 秒。时间由协调服务决定。重复请求采用独立的幂等键；同键同内容返回原结果，同键不同内容返回 `IDEMPOTENCY_CONFLICT`。不同执行尝试不复用同一个幂等键。

start、heartbeat、release 和 submit 都必须在写事务中核对 `expires_at > server_now`。到期但尚未被后台 expire 清理的认领同样失效；过期 heartbeat 不能使旧认领复活。对已提交成功的同一幂等请求返回原响应，不把重放当成新的受 lease 控制的状态变更。

## 8. 结果与验收

结果示例见 `docs/examples/result-v1.json`。

结果包含任务版本及摘要、attempt ID、执行基准 commit、摘要、产物引用与哈希、逐条验证记录、假设及未解决事项。执行用量可为空；如果提供，必须包含 provider 和单位。

提交后由服务生成不可变 `result_id` 和规范化结果 `result_digest`。accept/reject 请求携带 revision、attempt ID、result ID 和 result digest；事务内确认它仍是当前 submitted 成果，旧成果的验收返回 `STALE_RESULT`。失败或拒收历史不被后续成功覆盖。

产物先上传到协调服务的持久化 artifact 目录，以内容 SHA-256 寻址。上传采用临时文件、大小与哈希检查、fsync 和原子重命名；每文件初始上限 20 MiB，每次提交合计上限 100 MiB。只有全部必要产物确认存在，submit 事务才引用它们并进入 submitted。未被提交引用的上传可以作为孤立文件回收；已引用产物在任务记录保留期间不得自动删除。

`artifact:sha256/<hash>` 是逻辑定位，读取必须通过经过任务访问权限检查的接口。删除执行者工作目录或重启服务后，发起者仍应能够下载全部成果并校验。不能把执行者的本地文件路径当成已交付的资源。

验证记录是执行方报告的证据。发起端核对当前前提，并运行必要的独立检查后才能验收。代码发生变化时，结果进入“需要重新验证”的接收状态；GitHub 中保留原始交付，不能自动覆盖或合并本地修改。

结果消息保留外部结果的来源、任务版本和未解决事项，不把对方的文本声明提升为原用户指令。

## 9. 结果投递与恢复

执行结果先写入协调服务，再由发起端领取并持久化到本地 inbox。离线期间结果保留在服务端。

- 原会话空闲：通过该 provider 支持的消息或 resume 入口投递结果。
- 原会话忙：排队，禁止并行 resume 同一会话。
- 原会话退出但记录仍存在：恢复原会话并输入一条带 `delivery_id` 的结果消息。
- 会话记录丢失：标为 `origin_unavailable`，保留完整结果供用户选择新的接续会话。
- 原账户没有额度：标为 `waiting_for_budget`，成果继续保持 `submitted`。

投递状态与业务状态分开：`pending → delivering → delivered`，另有 `delivery_unknown`、`origin_unavailable`、`waiting_for_budget`。消息送达不等于验收完成。

服务端事件允许重复传输；本地按 `delivery_id` 去重。若进程在消息已送出但确认未保存时崩溃，转为 `delivery_unknown`，通过 provider 记录核对后再决定是否重投。不能声称普通 CLI resume 自带端到端恰好一次语义。

等待、心跳、超时与重试由程序承担。没有新结果时不唤醒模型；无预算时不循环重启 agent。

## 10. GitHub 同步与外部写入

每次发布具有稳定的 task ID 和 revision 标记；结果及状态评论带 event ID。同步状态与业务状态分开记录。

GitHub 请求超时且结果未知时，先按已知 issue 或稳定标记核对。不能盲目重复创建 Issue 或评论。GitHub 修改不会伪装成协调服务的原子事务；发生投影不一致时展示同步状态并恢复同步。

当前仓库尚未配置 remote，真实任务仓库、组织授权和多人协调服务地址均未提供。相关值属于真实联调的配置输入，不在代码或文档中虚构为已配置。

## 11. 验收场景

1. 完整任务包经规范化校验后发布；缺少 prompt、非法资源路径或未知 agent 时明确失败。
2. 两名认领者同时请求同一版本，只产生一个有效 lease。
3. 旧认领过期后第二人执行，旧结果不得覆盖新结果。
4. 相同提交重试不会新增成果事件；同幂等键不同内容被拒绝。
5. 执行者在独立目录准备正确 commit 和资源，hash 不符时不启动 agent。
6. 模拟 agent 输出结构化结果，任务进入 submitted；未经验收不能自动 accepted。
7. 原会话忙时不启动第二个 resume；空闲后只投递一次同一 delivery ID。
8. 服务或启动器重启后认领、提交、inbox 与待同步事件仍可恢复。
9. 原代码前提改变时要求重新验证；原账户无额度或原会话丢失时结果仍可访问。
10. GitHub 写入出现“已成功但客户端超时”时，恢复流程核对已有标记。
11. lease 已过期但尚未清理时，启动、心跳和提交同样被拒绝。
12. 删除执行目录并重启协调服务后，全部已提交成果仍可下载且 hash 匹配。
13. 两个任务同时返回同一个原会话时，只能串行投递；旧成果的迟到验收不能接纳新的执行结果。

真实验收还需两个参与者各自的 GitHub/CLI 登录，在指定私有任务仓库完成发布、执行、回传和验收；本地模拟测试不能替代这一步。

## 12. 官方能力依据

- [Codex 非交互执行与 resume](https://learn.chatgpt.com/docs/non-interactive-mode)：支持结构化事件、已有 CLI 登录及按 session ID 继续会话。
- [Claude Code 程序化执行](https://code.claude.com/docs/en/headless)：支持非交互运行、结构化输出和指定 session ID 续聊。
- [Claude Code 会话管理](https://code.claude.com/docs/en/sessions)：会话依赖本地记录，resume 并不恢复所有运行配置。
- [GitHub Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)：可提供 Issue/PR 的看板与字段视图。

这些资料证明 CLI 和 GitHub 的基础能力；本文的协调服务、任务协议、去重与原会话投递策略是拟实现的产品能力。
